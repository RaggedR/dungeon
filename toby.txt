Dear Toby,

1. Claude is a container morphism, not a container
--------------------------------------------------

I just had a long conversation with Neil, and the outcome of the conversation is that Claude is a container morphism not a container.

Suppose a monster in the game can do three things:
 - open a door
 - trade an object
 - attack

We would enforce this on the level of the unix operating system. We have a "wrapper" claude_wrapper which writes some kind of "flag" to a plain text file (which claude can't modify) before claude is executed. Then three "tool wrappers"
 - open_wrapper
 - trade_wrapper
 - attack_wrapper
Each tool wrapper would read from the plain text file and then execute the tool only if the flag is present. Then when it is finished, delete the flag. So no future tools can be executed until claude_wrapper is invoked again. We would set unix file permissions so that Claude can't spawn another instance of himself. Everything is enforced by unix file system permissions.

2. Personality, secret and desire
---------------------------------

Each monster has a "personality" which is just a markdown file that it reads on startup (CLAUDE.md). It can't write to this file. The markdown file tells claude what tools he has available and the conditions under which he should use them. For example: He should only open the door if the player can demonstrate, in English, by prompting the monster that he knows some secret that he perhaps learned from some other monster. It is a "fuzzy" decision, not a straightforward if/then.

Each monster has a "secret" and a "desire". So if you can satisfy its desire, either with an object, or with some information obtained from another monster, then you can "convince" it to help you (open a door or reveal a secret) rather than attack you. It might even be possible for you to "convince" one monster to attack another monster.

I would also like to introduce monsters that lie. But this is an added level of complication to the game. Maybe not in the first implementation. Just get a minimal working game first.

3. The description this came from
---------------------------------

Here's the original game description that I sent neil:

A party of three descends into a labyrinth, armed with daggers, to receive a sacred item and comes back up. The labyrinth is a tree of depth eight. It is generated as they descend and it does not exist until somebody tries to go there. The code of each level is generated by Claude, from an algebraic specification of that level which is also generated by Claude. The game carries an element of chance and the difficulty level can be configured.

Each level contains a maze (generated by Claude when he generates the level). Some of the doors are guarded by monsters, some of them are not. You can either kill the monster and take its items, try to convince the monster to open the door, or trade your items with the monster. Trap doors lead down into lower levels of the labyrinth. These are guarded by gate-keepers. To convince the gate-keeper to open the trap door you must solve a riddle, so some of the monsters also have clues.

There are 12 types of monsters and each type of monster has secrets and desires and subjects they enjoy talking about. The monsters are LLMs. You can either negotiate with them, chat with them, trade with them or try to kill them.

The monsters also have relics. There are ten types of relic, each of a different weight. The party can only carry 6 at a time (6 hands) one for each hand - including a dagger and a lamp. You can collect healing potions and lamp oil but these must be carried.

You must discover the monsters’ secrets and desires to solve the labyrinth. It is a turn-based console game with a finite list of possible moves at each turn - including negotiating with and chatting to the monsters. The monsters can lie, and some of the other monsters know that they are lying.

You can also come back up the labyrinth. The most valuable relics lie deepest in the labyrinth and you must go down into the labyrinth to collect them then come back up with the items to negotiate with the monsters who guard the doors on higher levels. The sacred object is on the top level guarded by a monster that you must trade with to open the door using a relic from the lowest level.

Coming back up the labyrinth is the backwards map of the container morphism of the game. Goals, like opening a door require sub-goals to be achieved first, like obtaining a relic or a secret, which in turn themselves require sub-goals to be completed. The list of open-subgoals travels forwards with the prompt as claude generates deeper levels of the labyrinth and their resolution travels backwards.

It is a simple turn-based console game. In the future we could add a simple GUI with a drop down menu of options, a way to view your inventory and an image for each room, monster and item (generated by Claude from a description using midjourney). Claude also generates the descriptions when he is generating the levels of the dungeon. Claude can draw from history, religion and mythology to add an element of creativity to the game. It could also be sci-fi.

things in it are load-bearing:

The win condition is epistemic. Before the game starts Claude draws a table — kinds of inhabitant, which type of relic each kind wants, each monster's interest, motive, secret. Your job is to discover that table.

The point of the game is to illustrate agentic container programming. That Claude can also generate the specification and implementation of each level, monster prompts, and images from descriptions is an added twist.

4. The tower of servers
-----------------------

Every level is a small typescript server. Level d listens on port 9000+d, and it is one Deno process. The same program runs on every port. Eight bespoke programs would be a game, but the same program composed with itself eight times is a claim about composition, and that claim is the reason for building it. The eight are not eight copies of the same content. Each one is started with a level specification and serves whatever that specification describes, so the program is fixed and the labyrinth is not.

A level is a container because it is prompted and something comes back. The prompt is a party arriving at the top of the level. The response is the party leaving, with whatever it is carrying and however much light it has left. That is the whole interface, and it is the same interface at every depth.

Descending is a delegation. The handler for a trapdoor on level d spawns a command-line tool which carries the party to the socket of level d+1, so the delegation is a real process with a real boundary and not a function call wearing a costume. A command-line tool is already a container. It receives one prompt, its argument vector, and it produces a response whose type depends on which prompt it was.

Nothing checks what crosses that boundary. A party goes down as text on an argument vector and the haul comes back as text on standard output, and no type survives the crossing. What arrives is bytes. Every type claimed above is established, if it is established at all, by a decoder on the receiving side. The type says what must be true and the decoder is the only thing that ever checks it. This matters most for the monsters, because there the thing on the other side of the boundary is a language model.

A level does not exist until somebody tries to go there. The trapdoor handler generates the specification for the level below, then generates the code from it, then starts the process. So the tower builds itself downwards as the party descends, and the party's own state is the prompt the next level is written against.

A monster is a server too, and the level it stands in is its client. The handler spawns the claude binary and answers with whatever comes back on standard output. From above there is no way to tell a monster from any other server here, and that is the whole claim.

None of this is speculation. The stalin game already runs five of these servers, with gosplan on 8801 delegating to agriculture, industry, transport and foreign trade on 8802 to 8805. There is an optional sixth on 8806 whose answers come from claude instead of from a rule, and starting it is the moment the game stops being reproducible from its seed.

5. A simplified algebra of the game
-----------------------------------

The full algebra is spread over two blocks of about two dozen lines, and this has twelve.

  game      =  descend ◁ receive ◁ ascend
  level(d)  =  room(d)
  room(d)   =  round ◁ room(d) ◁ exit(d)
  exit(d)   =  way(1) × way(2) × ... × way(k)
  way(i)    =  room(d) + level(d+1)
  level(9)  =  nothing
  round     =  move × talk × strike × trade
  talk      =  say ◁* (told + nothing + attacked)
  monsters  =  monster(1) ⊠ monster(2) ⊠ ... ⊠ monster(n)
  monster   =  words in, and one of eight actions out
  receive   =  ask ◁* (given + refused)
  ascend    =  the backwards map of everything above

Four operators, and one rule each. The tensor ⊠ means both parts are prompted and both replies are owed. The product × means both are offered and exactly one answers. The sum + means the prompt already belongs to one side before it is sent. The sequence ◁ means the second prompt is computed from the first response, and the starred ◁* means the first response decides which side is prompted at all.

6. Why the room is a tensor
---------------------------

The monsters standing in one room are a tensor product. Every monster in the room is prompted and every monster owes a reply, which is what distinguishes the tensor from the product. The ways out of a room are a product, because three ways are three prices and you have one purse, so taking one leaves the other two untaken.

The important thing about the tensor is that the independence is enforced rather than promised. The shape of a tensor is a record holding both prompts at once, so both prompts must be constructed before either one is sent. You cannot make the second prompt depend on the first reply, because you had to build it first. That is a fact about the type and not a fact about how the monsters happen to behave.

Which is why no monster may call another, and it is the one action we refuse rather than cost. A monster that summons is a monster whose action depends on another monster's action, and that is a sequence and not a tensor. Every other action leaves the algebra alone. That one would force the operator to change, so the answer is no.

And this is where the wrappers at the top of this letter come in. The type system can say that a room is a tensor. It cannot stop the claude binary in one monster from executing a command that starts another. The unix file permissions can, and that is the level the refusal has to be enforced at. So the algebra states the constraint and the operating system holds it.

7. Coming back up, and the goal tree
------------------------------------

The last line of the algebra above is an IOU, and this is what it stands for. Coming back up the labyrinth is the backwards map of the container morphism of each level, and the ascent applies those maps in the reverse of the order the descent applied the forward ones. That reversal is not bookkeeping. Compose two morphisms and work out the result, and the backward map of the deeper one applies first, so level eight's backward map runs before level one's. Which is exactly what ascending is, and it is the reason the labyrinth unlocks from below.

Goals require sub-goals. Opening a door requires a relic or a secret, obtaining that relic requires sub-goals of its own, and the recursion stops at goals the party can pay out of the purse it walked in with. So the goal structure is a container in its own right. The kind is which goal this is, and the positions over that kind are what must be discharged before it.

  goal ◁ sub
  W  =  μX. Σ_g X^sub(g)

The goal structure of a labyrinth is the W-type of that container, which is to say the well-founded trees over it. And the sum and the exponent are not a description written after the fact. They are the wire format. What travels forwards with the prompt is the positions not yet filled, which are the open sub-goals, and those are the exponent. What comes back up is their fillings, carried in hands, and those are the sum. That holds for the positions that are things. A position that is a secret comes back in the player's head instead, which is the subject of the last section of this letter.

The positions of a goal always lie deeper than the goal itself. So the goal tree is the level tree with its orientation reversed, and the relic from the deepest level opening the way at the shallowest is one edge of it drawn at full length. There are now two recursions over the same territory and they point opposite ways. The labyrinth is unfolded downwards on demand and does not exist until somebody goes there. The goals are folded upwards as things are carried home. Generating a tree and consuming one are not the same act, and the expensive one is always the consuming.

Two conditions make that tree exist and be worth anything, and a generator has to hold both. Acyclicity is well-foundedness, and without it a branch may descend for ever, so a cyclic desire graph is not an unfair labyrinth but not a goal structure at all. Every leaf must be payable from the purse the party walked in with, and without that the tree is well-founded and still unreachable. Neither should be checked. Generate the tree from the root and give every position a payer at a strictly greater depth than its parent, and then acyclicity is not a property you verified. It is a property you could not have written down.

8. The container as a TypeScript type
-------------------------------------

Here is how the algebra is actually a type. Everything below was compiled with deno 2.7.14 and typescript 5.9.2, and the errors are the real ones.

TypeScript has no dependent types, and it does not need them here. The response type has to vary with the prompt, which normally wants a function from values to types. But every prompt set in this game is finite, and over a finite index a function from values to types is just a lookup table. A tagged union is a finite index. So a container is written as the union of its fibres, one fibre per prompt, each pairing a prompt with the response owed to it.

  export interface Fib<S, P> { readonly shape: S; readonly pos: P }

  export type Action =
    | "attack" | "approach" | "withdraw" | "flee"
    | "bargain" | "offer" | "answer" | "refuse";

  export type MonsterC =
    | Fib<{ tag: "Say"; words: string },    Action>
    | Fib<{ tag: "Offer"; give: string[] }, string>
    | Fib<{ tag: "Look" },                  { weapons: number }>;

Three prompts and three different response types. Saying something to a monster gets you one of eight actions. Offering it goods gets you a sentence of English. Looking at it gets you a count of weapons. Those are not the same kind of thing, and which one you get is fixed by what you asked.

9. A secret is prose
--------------------

Notice that a secret comes back as a string and not as an object, and that is the most important line in the block. A secret is prose. The program does not keep it anywhere and it never enters the party record. The player has to hold it in their own head and work out where it is worth using. If a secret were an object then the client would have a list of them, and looking at that list would cost nothing, exactly as looking at the map and the inventory costs nothing. A free list of every secret you have been told is the table, filled in on your behalf. Discovering the table is the win condition, so a program that stored secrets would be a program playing its own win condition for the player.

There is a price for that and it is worth stating plainly. Players will keep notes on paper, so the game does not remove the inventory of secrets. It moves it outside the program, which is the right place for it. Paper does not sort, does not search, and does not tell you which of eleven remembered sentences is the one this gate-keeper wants. What the program refuses to supply is not the memory. It is the indexing.

It also puts information outside the morphism altogether. A relic travels up through the backwards map, carried in hands, and the type system can count it. A secret does not travel that way at all. It leaves the game as prose and it can only re-enter as prose the player typed at a monster. So the knowledge economy runs entirely through the text boundary described earlier in this letter, which is the one part of the whole design that nothing checks.

Which costs one of the type-level tables some of its force, and this is the part I am least sure about. A puzzle whose positions are relics stays checkable, because the party either holds three pieces or it does not, and a party holding two cannot be given an argument to make. A puzzle whose positions are secrets is checkable by nothing, because the party's knowledge is not in the program to be indexed. So the positions of a goal divide in two. The material ones are enforced by the compiler and the informational ones are enforced by a gate-keeper's judgment, and only the first kind can be made unwriteable.

10. The dependent lookup
------------------------

Two type-level functions read that union. The first collects the prompts, and the second is the dependent lookup.

  export type Shape<C extends Cont> =
    C extends Fib<infer S, unknown> ? S : never;

  export type PosAt<C extends Cont, S> =
    C extends Fib<infer S1, infer P> ? (S extends S1 ? P : never) : never;

A conditional type distributes over a union, so both of these compute by visiting every fibre. The lookup returns the response type of the one fibre the prompt lies in, and it returns nothing for a prompt that lies in no fibre. Watch the direction of that test, because it is the one place this is easy to get wrong. A prompt you actually hold is narrower than the fibre's declared prompt type, so the test has to be that your prompt extends the fibre's and not the reverse. Getting it backwards makes every lookup return the empty type, and the compiler then rejects every correct handler you write. I did exactly that on the first attempt.

11. The table, and the three things it checks
---------------------------------------------

Now the part that matters. A monster's implementation is a table of one handler per prompt, and the table is generated from the union rather than written out by hand.

  type At<K extends Shape<MonsterC>["tag"]> =
    Extract<Shape<MonsterC>, { tag: K }>;

  type Handlers = {
    [K in Shape<MonsterC>["tag"]]: (p: At<K>) => PosAt<MonsterC, At<K>>;
  };

  export const handlers: Handlers = {
    Say:   (p) => (p.words.includes("please") ? "answer" : "attack"),
    Offer: (p) =>
      p.give.length > 0
        ? "The west gate is unbarred on feast days."
        : "I want nothing you are holding.",
    Look:  () => ({ weapons: 2 }),
  };

The keys of that table are not a list somebody maintained. They are the prompts of the container, so the table cannot fall out of step with the interface. Three things are checked at once, and each of them is a different way of failing to be a container.

Delete the handler for Look and the table is incomplete.

  TS2741 [ERROR]: Property 'Look' is missing in type '{ Say: ...; Offer: ...; }'
                  but required in type 'Handlers'.

Have the monster answer with a ninth action and the response is outside its container.

  TS2322 [ERROR]: Type '"attack" | "summon"' is not assignable to type 'Action'.
    Type '"summon"' is not assignable to type 'Action'.
    Say: (p) => (p.words.includes("please") ? "summon" : "attack"),

Answer the right prompt with the wrong kind of thing and the dependency is broken.

  TS2322 [ERROR]: Type 'string' is not assignable to type '{ weapons: number; }'.
    Look: () => "attack",

Read the second of those again, because it is the claim at the top of this letter enforced by a compiler. A monster that decides to summon has not surprised the game. It has failed to respond within its own container, and the failure is a build error rather than a bug.

12. The boundary is bytes
-------------------------

And now the boundary, because none of what the compiler checked is checked out there. There are two crossings in this game and neither carries a type. One is a pipe and the other is a socket.

A pipe is a buffer the kernel hands out on request, with one descriptor to write into and one to read out of. The shell puts the writing end in the left program's slot 1 and the reading end in the right program's slot 0, and runs both at once. Nothing is checked. The interface between two programs is bytes, and any two programs can be joined. That is the strength of it. Nothing verifies that the composition means anything, and that is the cost. What a program promises is written in its manual page and nowhere else, so the only thing enforcing the promise is that somebody read it.

The socket is the same bargain in a smarter suit. HTTP is a request and a response and nothing else happens, which is already the question and the answer of a container. A request is a method, a path, some headers and possibly a body. A response is a three-digit status, some headers and a body. The party descends in the body of a request and the haul comes back in the body of a response, and the body is JSON. Fielding made the same decision Unix made and it paid off in the same way, so every web application in the world now speaks it. The price is also the same. JSON carries no types.

Which is worth saying exactly. The response type never crosses the wire. Only the prompt goes down. The response type is recovered on this side by the runner, which knows which prompt it sent, and that recovery is the dependent lookup of the previous section doing its work at run time rather than at compile time.

13. Validate, do not cast
-------------------------

So all input must be validated, and validated rather than cast. A decoder takes an unknown and returns either the response it ought to be or nothing at all. The keyword "as" is not a check. It is a promise to the compiler, and a promise from the far side of a pipe is exactly the thing that was never enforceable. Nothing is treated as a response until a decoder has said it is one.

The decoders are a table with one entry per prompt, and it is the same mapped type as the handlers. Delete one and the program does not build.

  TS2741 [ERROR]: Property 'Look' is missing in type
                  '{ Say: (u: unknown) => Action | null;
                     Offer: (u: unknown) => string | null; }'
                  but required in type 'Decoders'.

And this is the crossing that matters most, because the thing on the other side of it is a language model. Here is the decoder for Say, run against four things the claude binary might really put on standard output.

  a legal action     -> "withdraw"
  a ninth action     -> null, rejected at the boundary
  an apology         -> null, rejected at the boundary
  fenced JSON        -> null, rejected at the boundary

Read the last two. A model that answers a monster's prompt with an apology has not attacked, bargained or refused. A model that wraps its answer in a markdown fence has produced eleven characters of punctuation around a legal action. Neither is malice and both are ordinary, and both are stopped in the same place by the same three lines. The type says what must be true and the decoder is the only thing that ever establishes it.

The same rule covers the other direction, because the player is input too. What a player types is arbitrary text and it gets routed to whatever is listening. A word that names no interface is not a move the game refuses politely. It is a prompt that fails to decode.

And the honest scope of all of it, in one sentence. Validating buys that a monster's response is one of eight actions and that every reader of it has had to handle eight cases and no more. It does not buy that the eighth was deserved. A player who talks a gate-keeper into opening the way has not escaped the type system, and there is nothing in a decoder that could ever have an opinion about that.
